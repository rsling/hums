# Guardrails

Authoritative, together with `CLAUDE.md` (rules, glossary, layers) and `docs/SCHEMA.md` (document model). Items tagged **[Dn]** are defaults whose status is in `docs/DECISIONS.md`. `CLAUDE.md → Guardrails` carries the one-line summary; this file is the full contract.

Roland is the only maintainer and will not read every line. Structure therefore has to be enforced by the test run, not by review. These checks exist so that drift fails loudly while nobody is watching. They land in milestone 1, before there is anything to protect, and run on every `ctest`. Every script has a fixture in `tools/fixtures/` that must make it fail; that negative run is itself a test.

## 1. Schema names live only in `Ids.h`

`tools/check_identifiers.py` parses `src/model/Ids.h`, collects every string literal used to construct a `juce::Identifier`, and scans the rest of `src/` for those literals **inside Identifier construction and property/child APIs** (`juce::Identifier (`, `getProperty (`, `setProperty (`, `getChildWithName (`, `hasType (`, `ValueTree (` and friends). A bare word like `name` in a comment or a UI label is not a hit. Any hit outside `Ids.h` fails the check with `file:line`.

Allowed exceptions, and only these: `src/io/Migrations.cpp`, which by definition must name properties that no longer exist, and `tests/io/fixtures/`. Both are listed explicitly in the script — not matched by a wildcard. View-state identifiers under `UiState` are not an exception; they live in `Ids.h` too.

The script can only trust an `Ids.h` it can read completely, so it also fixes the form of that file: every declaration is `inline const juce::Identifier pitch { "pitch" };`, one per line, the constant named exactly like its string. Anything else in `Ids.h` that mentions an `Identifier` fails the check. In every one of the named calls the name is the first argument (`juce_ValueTree.h` at the pinned tag), and that is where a literal counts as a hit, on whichever line it stands; what follows it is a value, and a value is not a name even when it equals one: `event.setProperty (ids::kind, "cc", …)` passes, although `cc` is also a property. In a `ValueTree` constructed with its properties and subtrees, the names are the type and the first half of each pair, in a subtree written as a list in braces too. The brace after a trailing return type (`[] () -> juce::ValueTree {`) opens the body of a lambda and is no construction. `node["pitch"]` and `juce::Identifier x = "pitch"` count as well; a subscript opens with a bracket that is code, so the brackets in `text << "[" << position << "]"` are text and what stands between them is no name. A string that merely equals a schema name outside those places (`text == "cc"`, a label) is not a hit.

**Wherever an Identifier is expected.** `juce::Identifier` converts from a string literal without a word, so a literal compiles wherever an Identifier is expected, not only in JUCE's own calls. The script therefore looks at four more places, and there only at the literal that stands for the name:

- **A function of ours with a `juce::Identifier` parameter** — `PropertyReader::getInt (node, "pitch", 60)`, `Settings::writeTick`. These are not a list kept by hand: the script reads every declaration under `src/`, lambdas held in a variable included, and remembers which parameters of which function are an Identifier, as it reads the names from `Ids.h`. A call is checked at exactly those arguments, so a value is still not a name: `PropertyReader::getString (node, ids::kind, "cc")` passes. Calls are matched by the function's name alone; two functions of one name in different classes are checked alike.
- **What a function returns** — a literal in a `return` of a function, or of a lambda with a named return type, that returns an Identifier or a list of them. A function or such a lambda that returns a `juce::ValueTree` can return a list in braces (`return { "Event", { … } };`), because the constructor that takes a type and its properties is not `explicit`; that list is checked like any other `ValueTree` construction.
- **A list of Identifiers** — `std::array<juce::Identifier, 2> { … }`, a `std::vector`, a plain array.
- **XML tag and attribute names** — the first argument of `juce::XmlElement`'s constructors and of its calls that take a name (`hasTagName`, `getIntAttribute`, `setAttribute` and the rest; the list in the script is the one in `juce_XmlElement.h` at the pinned tag). In `model/`, `io/` and `render/` only: there every XML element is the project file, in `app/` it can be something else.

A schema name in one of these places is a hit in every layer (XML names excepted, as said); a name that is no schema name is a hit under the next rule. What the script cannot see is a name that reaches such a place through a variable (`const char* name = "pitch";`): it reads text, not types.

**Invented names [D15].** The rule above knows only the names in `Ids.h`, so on its own it would let `node.setProperty ("swing", …)` pass. Two things close that. In `model/`, `io/` and `render/`, where every ValueTree is the document, the script refuses *any* string literal in the place of the name: the first argument of one of the named calls, the names of a `ValueTree` construction, the initialiser of a `juce::Identifier`, a subscript, and each of the four further places above. A value is not a name: `setProperty (ids::kind, "event", …)` passes. `views/` and `app/` keep the first rule only, because there the same call names can belong to things that are not the document (a `juce::DynamicObject`, a component's properties), and views may not write the document anyway. `src/io/Migrations.cpp` stays exempt from both rules. The second thing is a runtime check in guardrail 3, below.

The fixtures are small trees under `tools/fixtures/check_identifiers/`, one planted violation each: a literal in `getProperty`, `setProperty`, `hasType`, `getChildWithName`, a subscript, a subscript beside two brackets that stand in string literals and are no hit, a subscript after a number with a digit separator (`1'000`) beside a comment after such a number that is no hit, an `Identifier` constructed and one initialised with `=`, a `ValueTree` constructed; a name in a call beside a value that equals a schema name and is no hit, the same in the property list of a `ValueTree`, and the type of a subtree; a lambda with `-> juce::ValueTree {` and one with `-> juce::Identifier {`, each with one name in its body beside a value that equals a schema name and is no hit; four invented names, one each in `model/`, `render/` and `io/` and one in a property list; for the further places a function of ours with the Identifier as its second parameter and one with it as its first (beside a value that equals a schema name and is no hit), a lambda, a `return`, a list in braces returned as a `ValueTree` from a function and from a lambda, a `std::array` and a plain array, an XML tag name tested and one constructed, and three more invented names: through a function of ours, in the `return` of a lambda, and as an XML attribute — all scanned against the real `Ids.h` — and two stand-ins for `Ids.h` itself, one whose constant differs from its string and one with a declaration in another form. Each fixture's test passes only when the script reports that file, that rule, and exactly one violation.

## 2. The layer rules are checked, not just documented

`tools/check_layers.py` walks the `#include` lines under `src/`, resolves quoted relative paths, and enforces the table under `CLAUDE.md → Layers and dependencies`, including the render-core std-only rule (`render/snapshot/`, `TempoMap`, `Kernel`, `NoteTracker` include only std and each other, so the engine's dependency on them is transitively clean without a transitive check) and the transitive check that `app/TransportFacade.h` pulls in no other `engine/` header. It also enforces the platform rule: OS headers (`CoreMIDI/`, `CoreFoundation/`, `CoreAudio/`, `mach/`, `Cocoa/`, `AppKit/`, `Foundation/`, `objc/`, and any angle-bracket include that is neither std nor JUCE) may appear only under `src/platform/mac/`; `.mm` files exist only under `src/platform/mac/`; `platform/` interface headers include only std and each other; nothing outside `app/` and tests includes `platform/mac/`. `views/` including any other `engine/` header, `engine/` including anything from `model/` or from `render/` outside the core, a render-core file including JUCE, and an OS header outside `platform/mac/`, are the failures this check exists for.

So that nothing escapes the table, the check also refuses what it cannot assign to a layer: a source file under `src/` outside the layer directories; a quoted include that names no file under `src/` with exactly that spelling (compared case-sensitively, although the macOS file system is not; std, JUCE and OS headers are included with `<...>`); an include that leaves `src/`; and an `#include` with a macro in place of a file name. Quoted includes resolve as the compiler resolves them, beside the including file first, then from `src/`. "Std" is the list of C++20 standard headers in the script; `<stdint.h>`-style C names are not on it. Every include line counts, also one inside `#if 0`.

The check reads a file only when its suffix says it is source (`.h`, `.cpp`, `.mm` and the few others listed in the script), and the compiler includes a file of any name. A header named `Detail.hxx` would therefore be included without complaint and could itself include anything, and the walk from `TransportFacade.h` would end at it. So `src/` is a closed world: every file in it either has one of the listed suffixes, spelled exactly so (`.H` and `.MM` are not on the list), or is one of the files the script names as not source, `CMakeLists.txt` and `.DS_Store`, by exact name and never by a wildcard. Any other file fails the check, an editor's backup copy included; delete it or move it out of `src/`.

Quotes are for our own headers and angle brackets for std, JUCE and OS headers, and the check holds both halves. `src/` is on the include path, so `#include <engine/Transport.h>` compiles like the quoted form; in `platform/mac/`, where an angle include that is neither std nor JUCE is allowed, it would pass for an OS header and never meet the table. An angle include that names a file under `src/` therefore fails in every layer, also where the table would allow the header in quotes. It is compared without regard to upper and lower case, because that is how the macOS file system finds it. An angle include with `..` in it fails too: such a path can leave its include directory and come back into `src/` under a name the check cannot follow, and no std, JUCE or OS include needs one.

The fixtures are small trees under `tools/fixtures/check_layers/`, each standing in for `src/` with one planted violation, one per failure class: `views/` including `engine/` and an `app/` header other than the facade; `engine/` including `model/`, `render/` outside the core, and `platform/mac/`; `model/` including `io/`; the render core including `model/`, the rest of `render/`, and JUCE; a `platform/` interface including JUCE and a backend; an OS header in `engine/` and in `app/`, a third-party header in `model/`; a `.mm` file in `app/`; a header of ours in angle brackets in `platform/mac/`, one in `views/` that the table would allow in quotes, one spelled in another case, and an angle include with `..`; `TransportFacade.h` reaching `engine/` through a second header; the four unassignable cases above; and two files the check would not read, a header with a suffix that is not listed and a `.MM` file. Each fixture's test passes only when the script reports that file, that rule, and exactly one violation.

## 3. Invariants as property tests, not examples

`tests/guardrails/` holds a small generator that builds random *valid* documents (a few tracks, clips of both kinds, placements, lanes, slots, automation lanes) and applies random sequences of commands from `model/commands/` — valid ones *and* deliberately invalid ones (overlapping placements, zero-length loops, notes into an automation clip). After every command it asserts all twelve invariants from `docs/SCHEMA.md` via the Validator, plus:

- a valid command fully applies; an invalid one leaves the undoable subtree XML-identical and the undo history unchanged;
- undo restores the undoable subtree to an XML-identical state, and redo returns to the post-command state (`UiState` excluded from the comparison);
- canonical save → load → canonical save is byte-identical;
- clip ids referenced before a command still reference a clip of the same `kind` after it, or the command was a conversion;
- every node type and property name in the undoable subtree is declared in `Ids.h` **[D15]**: a command that writes an invented name fails here, however its source is spelled. (The generator builds its documents itself, so the unknown properties a file from a newer build may carry do not occur.)

Seeds are printed on failure and reproducible. When the generator finds a failure, shrink it to a minimal document and add that as a named regression test.

A document is made from its seed and nothing else, its ids included, so one seed is one document on every run. The run goes through the seeds from 1 upwards; two environment variables say otherwise, because CTest hands no arguments to a test: `HUMS_PROPERTY_SEEDS` is the number of seeds (without it 1,000 in the plain configuration and 200 in the instrumented ones, set in `tests/guardrails/CMakeLists.txt`), `HUMS_PROPERTY_FIRST_SEED` the first of them. A variable that holds no such number fails the run. The run stops at the first seed that fails and prints it with the line that repeats it alone (`HUMS_PROPERTY_FIRST_SEED=<seed> HUMS_PROPERTY_SEEDS=1`). The generator has tests of its own: the same seed gives the same document, and the documents of the first 300 seeds together hold every node type and every property `Ids.h` declares, so a name added to `Ids.h` fails the run until the generator builds it. Each of the checks on a document (Validator, declared names, save → load → save) is shown once to find a planted fault.

The commands join the same run. After its document has passed, a seed applies twelve random commands to it (`tests/guardrails/CommandDriver`), about seven in ten in a valid form, the others in an invalid one, each as a gesture of its own in one undo transaction. A command that changes a clip gets an edit context of its own, of either policy, at pool level or through some of the clip's references, and in an invalid form also through a reference that is none of the clip's; the driver's test holds the run to reach a make-unique clone. `tests/guardrails/CommandChecks` holds each to the list above; a command that is applied and performs nothing must have changed nothing, and the document checks are run again only on a document whose text the command has changed, since the same text can only pass the same checks. Now and then the run takes the last change back and leaves it so, so that the next command meets a history with something to redo. A failure names the seed, the number of the command within it, and the command with its arguments. The sequence of commands is the same on every run of a seed; the ids of the nodes that commands add are not, because a command makes them with `juce::Uuid`. The driver holds every command of `model/commands/` in one table, and a test of its own shows that the first 100 seeds reach each of them applied in a valid form and, where it has one, refused in an invalid form, so a command added to the table and never reached fails the run; a command that is not in the table is not held to anything, and adding it there is part of the task that writes it. Each of the checks on a command is shown once to find a planted fault: an invalid document, an invented name, a valid command refused and an invalid one applied, a refusal that changed the document or the undo history, a change undo does not take back or does not know of, a transaction begun by the command itself, a referenced clip that changed its kind or is gone.

## 4. Render golden files

Every rendering rule in `docs/RENDERING.md` gets a pair in `tests/render/golden/`: a fixture project (XML, real UUIDs) and the expected event list, plain text, one event per line, `tick track channel type a b [data]`, **in emission order, not re-sorted**, SysEx with the full payload. The render test runs Kernel + NoteTracker over the fixture's full range and diffs against the file. Expected files are reasoned out by hand from the rules, never produced by the renderer under test on first creation.

Required cases, at minimum: skipped column; `resetAt` shorter than `stepCount`; `gate > 1.0` into a different pitch; `gate > 1.0` into the same pitch (merge); gate reaching into a skipped column; gate across the loop point into a different pitch, and into the same pitch (retrigger, not merge); `fixedPitch` lane ignoring cell pitch; off-cell CC values; placement `offset`; placement shorter and longer than the clip loop; two placements of one clip restarting (offset 0) and phase-continuous (merged); split during a held note; same-pitch overlap on one track and across two tracks on one destination; bank-select → program change → note at one tick; note-off and note-on of one pitch at one tick; AutomationLane overriding, passing through, and restoring the underlying value at exit; a lane whose first event comes after its placement start; two lanes overriding the same CC; event-clip note crossing `loopLength`; content past `loopLength` silent; `quantise` at `1/8` and `1/8T`; `quantise` moving an onset across the loop point (wraps to 0) in a loop that is not a multiple of the grid; two notes of one pitch quantised onto one tick; transport loop wrap with a held note; chase at a seek target: value found in the current placement, in an earlier iteration of it, in an earlier placement, and no value at all; export range cutting a note; a track with no Player rendering normally.

Golden files are regenerated only through the `regenerate_golden` target (which sets `HUMS_REGENERATE_GOLDEN=1`), and the diff is read before it is committed. A silently regenerated golden file is worse than no test — it turns a behaviour change into a green build.

## 5. Loading is a wall

`tests/io/` loads every fixture in `fixtures/` through the real load path: valid files install; files with a higher `schemaVersion`, malformed XML, invariant violations, and a fixture whose migration throws are all refused with the current document and the source file untouched. Save failure (read-only target) leaves the previous file intact.

The fixtures are whole project files under `tests/io/fixtures/`. The files directly in that directory are valid and must install. The files under `refused/` must be refused: an empty file, a text that is no XML, a file that ends in the middle, an unknown entity, an attribute twice on one node, text after the root node, a second root, a closing tag with another name than its node, a last closing tag cut short, a byte that is no UTF-8; a root that is no `Project`, a DOCTYPE, text between nodes, an attribute plain and as `base64:` on one node; a `schemaVersion` that is absent, is no number, or is too new; and at least one file per invariant 1 to 12. Each file refused for its content is `all_node_types.xml`, a valid fixture, with one thing changed, and says in a comment on its first line what. The tests (`tests/io/ProjectFileTest.cpp`, their names begin with `guardrail 5`) list every fixture with the outcome it must have and, for a file the Validator refuses, the one node and property; a file under `fixtures/` that is not in that list fails the run, so a fixture cannot be added and never loaded. A refused load must also tell a listener on the document nothing, and "untouched" for the file means its bytes and its modification time. No migration step exists at `schemaVersion` 1, so `refused/migration_throws.xml` is a valid file to which the test hands a step that throws; a file of the old version that the step cannot migrate takes its place with the first real step.

## JUCE pin

Not one of the five numbered guardrails, but a script with the same teeth. `libs/JUCE_VERSION` names the release tag JUCE is pinned to (`CLAUDE.md → Toolchain`); nothing else ties that file to the commit the submodule is at. `tools/check_juce_pin.py` fails when the commit checked out in `libs/JUCE` does not carry the pinned tag, or when the commit the repository records for `libs/JUCE` (the index entry, which is what the next commit would contain) is not the commit checked out there. So a moved submodule, a moved pin file, and a staged move that was never checked out all fail the gate. The fixture is `tools/fixtures/check_juce_pin/JUCE_VERSION`, a pin file naming another tag.

## How the scripts are run

The guardrail scripts in `tools/` are Python, standard library only, run with the Python that ships with the pinned Xcode (`xcrun python3`, `TOOLCHAIN.md`). Each is registered in `tests/guardrails/CMakeLists.txt` twice: against the repository, where it must exit 0 (`guardrail_<name>`), and against its fixture, where it must report a violation (`guardrail_<name>_fixture_fails`, or `guardrail_<name>_fixture_<case>_fails` when a script has several). A script exits 0 when the rule holds, 1 on a violation, 2 when it could not run; every violation is printed as a line starting `<script name>: VIOLATION`. The fixture run is judged by that line, not by the exit code, so a crashing script or a missing Python can never pass for a detected violation.

## Sanitizer builds

C++ compiles lifetime and threading bugs without complaint, and the likeliest ones here — a listener outliving its `ValueTree`, a `Component` deleted inside its own callback, a Snapshot retired while the engine still reads it — can run fine for weeks. So the test suite runs in three configurations, and `tools/gate.sh` runs them in sequence:

- **plain** Debug — the fast inner loop, `ctest` as before;
- **ASan + UBSan** (`HUMS_SANITIZE=address`) — the whole suite, built with `-fsanitize=address,undefined -fno-sanitize-recover=all`, so a UBSan finding fails the test instead of printing and carrying on;
- **TSan** (`HUMS_SANITIZE=thread`) — the engine tests: FIFOs, command queue, snapshot handoff and retirement. These tests run real producer and consumer threads; a single-threaded simulation gives TSan nothing to see.

The flags are set once at the top of `CMakeLists.txt`, before JUCE and Catch2 are added, so everything in the binary is instrumented. The instrumented configurations are single-config Ninja builds in `build-asan` and `build-tsan`.

- A sanitizer report is a failing test. `no_sanitize` attributes and suppressions for code under `src/` or `tests/` count as weakening a guardrail (`CLAUDE.md` rule 12). If the pinned JUCE itself trips a sanitizer, the suppression names that one JUCE symbol in `tools/sanitizers/`, with a comment saying why.
- **Canaries.** `tests/guardrails/` holds three tiny programs with one planted bug each — heap use-after-free, signed overflow, data race — built only in the instrumented configurations. Each passes only when its sanitizer reports the planted bug, so a build that has silently lost its `-fsanitize` flags fails the gate. The ASan and UBSan canaries also fail when the program runs on past its planted bug: UBSan prints the same report with or without `-fno-sanitize-recover=all`, and only running on shows that the flag is gone. Same idea as the negative fixtures for the scripts.
- **JUCE reports fail a test.** A failed `jassert` and JUCE's leak detector only print a line (`JUCE Assertion failure …`, `*** Leaked objects detected …`); outside a debugger the process still exits 0, and CTest would call the test passed. Every test executable is therefore registered through `hums_discover_tests` (`tests/CMakeLists.txt`), never through a bare `catch_discover_tests`, and that function makes either line fail the test, in all three configurations. Two programs in `tests/guardrails/` with one planted bug each — a failed `jassert`, a leaked object — are registered as tests that must fail (`guardrail_juce_report_assertion`, `guardrail_juce_report_leak`), so a pattern that no longer bites fails the gate. Debug builds only; a Release build compiles both checks out. The leak detector sees only classes that carry `JUCE_LEAK_DETECTOR`; JUCE's own classes do; a class of ours is covered only if it carries the macro too.
- The full gate runs before every commit **[D9]**; plain `ctest` is for the loop in between. Its plain run also builds `tools/miditiming`, which no test links, so a change that breaks the timing tool fails the gate and not the next timing check. The property generator may run fewer seeds in the instrumented configurations than in the plain one.
- Sanitizers find only what gets executed, and the GUI is not in the test suite. The manual checklist is therefore run on the ASan + UBSan build of the app.
- Timing is never measured on an instrumented build: `miditiming` and the milestone 0 and 3 numbers come from a plain Release build.
- Xcode's clang is not expected to ship LeakSanitizer; leaks stay with JUCE's leak detector, which is on in Debug and whose report fails the test (*JUCE reports fail a test*, above). Verify on the pinned Xcode at milestone 0 and record the result in `TOOLCHAIN.md`.
- RealtimeSanitizer is not shipped by the pinned Xcode, so there is no fourth configuration **[D10]**. A possible later guardrail for the engine thread's no-allocation / no-lock rule is compile-time: `[[clang::nonblocking]]` on the engine-thread entry points and `-Wfunction-effects` promoted to an error for `engine/` and the render core. Adding it is a guardrail change and is discussed with Roland first.

## Manual checks

`docs/MANUAL_CHECKS.md` is a short script run at each milestone boundary: selection, dragging, undo across tabs, focus and keyboard shortcuts, tab switching during playback, device unplug/replug during playback, sleep/wake, close with unsaved changes, recovery-file offer. Run on the ASan + UBSan build of the app (*Sanitizer builds*). Not automated; not optional.

## External review

Optional, at milestone boundaries only, never per commit. Give the reviewer a read-only checkout, `docs/SCHEMA.md`, `CLAUDE.md` and the other files in `docs/`, and a fixed question list; do not tell it what the code is supposed to do beyond those documents, and never say the code is believed correct — a reviewer primed that way stops finding things. Ask for a ranked, capped list. Findings that matter become guardrail tests; the rest is discarded, not archived.
